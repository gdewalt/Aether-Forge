---
name: Splitting a monolithic single-file HTML game into ES modules
description: Mechanics and pitfalls of converting a large single-file vanilla-JS HTML app into multiple ES module files without changing behavior.
---

When asked to split a large single-file HTML app (game, tool, etc.) into a multi-file project while preserving exact behavior:

- Do the split mechanically (script-driven), not by hand-rewriting: extract top-level `function`/`const`/`let` declarations, group them into logical files, prefix each with `export`, then auto-compute cross-file imports by scanning identifier usage. This avoids introducing subtle logic bugs from manual retyping across a ~4000-line file.
- After splitting, verify losslessness by reconstructing the concatenated body from the generated files (stripping added `export` keywords, import lines, and any intentionally-injected setter lines) and diffing it against the original extracted source with the `diff` command. Trust `diff`'s line-level output over a custom aligner script — a custom verifier is easy to get subtly wrong (e.g. misaligning after a multi-line construct) and produces false-positive diffs that waste time to chase.
- **Cross-file mutable `let` reassignment is the main structural hazard.** ES module imports are read-only bindings — a file that does `import { x } from './other.js'` cannot do `x = ...`. Any top-level `let` that's reassigned (not just mutated in place, e.g. `x.prop = 1` is fine but `x = null` is not) from outside its declaring file needs a paired exported setter function (e.g. `setX(v){ x = v; }`), and the importing file must call the setter instead of assigning directly.
  - Do not assume you've found all such variables by inspecting only the ones you expect — grep every `export let` name across all generated files for `\bvarName\s*=[^=]` (assignment, not comparison) and check which files it appears in. Vite/esbuild will fail the build immediately with "Cannot assign to import" if one is missed, so this class of bug is very cheap to catch by just running the dev server — but it's faster to grep proactively than to build-fail-fix-repeat one variable at a time.
- If the app builds UI via `innerHTML` template strings with inline `onclick`/`onmouseenter`/etc. handler attributes (common in vanilla-JS single-file apps), those referenced function names must be explicitly exposed on `window` (e.g. `Object.assign(window, { fnA, fnB, ... })`) in the entry/boot file after importing them from their owning modules — inline HTML attribute handlers only see `window` globals, not module-scoped bindings.
- When mounting inside a React shell for a Vite artifact: keep the vanilla game entirely separate from React. The React component should only render the static DOM containers the vanilla code expects (e.g. `#hud`, `#screen`, `#tooltip`) and dynamically `import()` the game's boot module once in a `useEffect` — do not port any game logic into React state/idioms.
- Set `allowJs: true, checkJs: false` in the artifact's `tsconfig.json` (plus a `// @ts-nocheck` header in each generated `.js` file) so the ported vanilla JS bundles via Vite without being subjected to the workspace's strict TypeScript settings.
